## Direction options

1. **Design medication revisions before adding editing.** Medication APIs offer
   add/archive/delete but no update (`convex/medications.ts:17-89`), while
   history joins logs to the medication's current fields (`convex/logs.ts:366-396`).
   A revision model would support real prescription changes without rewriting
   history, but it needs an explicit effective-date and snapshot policy first.
2. **Let primary caregivers revoke or resend pending invitations.** The task is
   already recorded in `TODO.md:1`, and settings renders pending invites without
   actions (`settings.tsx:1274-1313`). Revoke is the safer first increment;
   resend must rotate expiry/token state and handle concurrent acceptance.
3. **Finish the report export surface.** The backend already assembles a report
   preview (`convex/logs.ts:419-567`), but the PDF button is inert. Decide whether
   the real user need is printable HTML, PDF, or CSV before adding a heavy client
   dependency.
4. **Spike source-backed medication context.** `medicationLabels` already models
   provenance and staleness (`convex/schema.ts:108-118`), and `PLAN.md:22-26`
   names DailyMed/openFDA. Treat this as a read-only data-quality spike; do not
   derive personalized dosing advice from label text.

## Findings considered and rejected or deferred

- Changing the conservative once-daily RxNorm schedule default was not promoted:
  `PLAN.md:123-133` records it as an explicit product decision. The document is
  internally more cautious at `PLAN.md:28-38`; reconcile that wording separately
  rather than silently reversing the implementation.
- A settings-route split is deferred until plan 002 provides characterization
  coverage; refactoring optimistic cache behavior without tests has poor leverage.
- Deleting `src/lib/mock-data.ts` is safe-looking but lower priority than exposed
  APIs, privacy defaults, and medication-time correctness.
- Full dependency modernization is not recommended in plan 001. Patch reachable
  advisories within compatible release lines first; evaluate major upgrades in
  separate migration work.
